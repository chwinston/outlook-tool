## B5.3 — verify hardening (picked approach)

Combined two techniques from the spec:

1. **Settle delay** — `verify_delay_ms` (default 1500ms, env `OUTLOOK_TOOL_VERIFY_DELAY_MS`) sleeps between the AppleScript write and the verify scan. Directly addresses the diagnosed sync-lag cause.
2. **Count-based verify** — `verify_use_count_check` (default True, env `OUTLOOK_TOOL_VERIFY_USE_COUNT`) compares source folder count before and after the move. If count dropped, treat as success even when fingerprint scan can't find the row (large Deleted Items / Archive).

Why not EntryID-based verify (option 2 in the spec)? AppleScript indices SHIFT after a move — re-fetching message `N` after moving message `N` would return a different message. The count-delta approach is cleaner and works both per-message and in bulk.

## B5.2 — bulk-move primitive (Shape A)

`_AppleScriptBackend.move_bulk(moves, source_folder)`:

- Pre-fetches state for each message so `before_state` is populated.
- Calls `ensure_folder` once per unique target OUTSIDE the tell block (make-folder is not safe to mix with move-message in one transaction).
- Emits ONE `tell application "Microsoft Outlook"` block that first binds every message reference (`set m1 to message I1 of inbox`, ...`set mN to message IN of inbox`), THEN issues all `move` commands. The Shape A invariant — bindings before mutations — is tested explicitly (`test_tell_block_captures_refs_before_moving`).
- After the tell block exits: settle delay + count-delta check on source folder.
- If count dropped by `N` for `N` moves → all succeed as count-only "unverified-success". If count dropped by `k < N` → fall back to per-message fingerprint verify.
- A tell-block exception is NOT trusted — the entire batch is marked failed with a shared error message, because we cannot know which moves landed before the error.

`OutlookClient.move_bulk` + `delete_bulk` dispatch on backend. COM/Graph fall back to a serial loop (bulk primitives for those backends are Bolt 5 non-goals).

## Reporter adjustment (post-sweep)

The sweep surfaced a reporter optics issue: when bulk count-delta == N (all moved), the per-message target-presence scan was skipped intentionally for throughput, and the reporter marked those rows `verified=False` → "UNVERIFIED-success". That's misleading: count-delta on source is a **stronger** signal than the single-message source-absence fingerprint scan we trust elsewhere (count can't be fooled by same-fingerprint neighbors).

Patched the fast-path branch to set `verified=True` on all-succeeded bulk moves. Target-presence is now documented as "intentionally skipped on bulk fast path; count-delta is primary." Next sweep's reporter will correctly show `verified-success` instead of noise-tier `UNVERIFIED-success`.
